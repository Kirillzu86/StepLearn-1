# StepLearn — Backend (Django REST Framework)

Полноценный бэкенд платформы онлайн-обучения StepLearn на Python 3, Django и Django REST Framework (DRF), совместимый с React/Vite фронтендом и Nginx/Docker/Coolify инфраструктурой.

## Модели базы данных (`api/models.py`)

1. **`User` (кастомная модель на базе `AbstractUser`)**:
   - `username`, `email` (уникальный), `password` (хешируется PBKDF2/SHA256).
   - `avatar_url` (ссылка или base64 аватарка до 5MB).
   - `role`: `student`, `teacher` или `admin`.
   - Свойство `.name` — возвращает имя или логин (для обратной совместимости с React фронтендом).
2. **`StudentProfile` и `TeacherProfile`**:
   - Отдельная запись One-to-One для аккаунта соответствующей роли.
   - Профиль создаётся автоматически при создании аккаунта; миграция заполняет
     профили для уже существующих учеников и преподавателей.
3. **`Course`**:
   - `title`, `description`, `price` (0 = бесплатно, >0 = платно).
   - `rating` (по умолчанию 4.5+).
   - `author` (связь с `User`, создавшим курс).
   - `students` (`ManyToMany` через таблицу `Enrollment`).
   - `created_at` (дата создания).
4. **`Question`**:
   - `course` (`ForeignKey` на курс).
   - `text` (текст вопроса теста).
5. **`Answer`**:
   - `question` (`ForeignKey` на вопрос).
   - `text` (текст ответа).
   - `is_correct` (булевый флаг правильности ответа).
6. **`Enrollment` (запись на курс и отслеживание прогресса)**:
   - `user`, `course` (уникальная пара `user + course`).
   - `current_index` (номер текущего вопроса).
   - `progress_percentage` (процент прохождения 0-100%).
   - `completed_lessons` (количество пройденных уроков/вопросов).
   - `correct_answers` (количество верных ответов).
   - `created_at`, `updated_at`.

## Доступные маршруты API

Все маршруты доступны **как с префиксом `/api/`, так и без него** (например, `/auth/login` и `/api/auth/login`), что предотвращает ошибки при проксировании через Nginx и при локальном Vite dev-сервере.

|---|---|---|
| `GET` | `/v1/courses` (или `/api/v1/courses`) | Публичный каталог опубликованных курсов; преподаватель видит собственные курсы (поддерживает поиск `?q=...`) |
| `POST` | `/v1/courses` (или `/api/v1/courses`, `/v1/courses/create`) | Создание курса; требуется JWT teacher/admin, автор берётся из токена |
| `GET` | `/v1/course/{id}` (или `/api/v1/course/{id}`) | Опубликованное описание публично; draft/archive доступны только автору и администратору. Материалы видны автору, администратору или записанному ученику; заблокированный урок возвращается без содержания |
| `PATCH` | `/v1/course/{id}` (или `/api/v1/course/{id}`) | Изменение метаданных и статуса (`draft`, `published`, `archived`); только автор курса или администратор |

| `POST` | `/v1/courses/{id}/quiz/submit` | Проверка всех ответов quiz на сервере; записываются фактическое количество верных ответов и завершение курса без уроков |
| `POST` | `/v1/courses/{id}/complete` | Отметить завершённым только назначенный опубликованный текстовый курс без отдельных уроков и quiz; требуется JWT ученика |
| `GET`/`POST` | `/v1/courses/{id}/assignments` | Список доступных заданий курса или создание задания типа `text`, `short_answer`, `quiz`, `multiple_choice`, `file_upload` или `code`; опубликованный Code Assignment требует минимум один hidden test и выполняется отдельным изолированным runner |
| `GET`/`PATCH`/`DELETE` | `/v1/assignments/{id}` | Просмотр задания учеником или автором; редактирование и удаление — автором/администратором; удаление запрещено после отправки ученических ответов |
| `GET`/`POST` | `/v1/assignments/{id}/submissions` | Ученик отправляет текст, `source_code` (до 50 000 символов) для задания `code`, `{answers: [{question_id, option_ids}]}` для теста или multipart-файл (PDF/TXT/PNG/JPEG до 10 МБ); code submission создаётся со статусом `pending` и передаётся в isolated runner, quiz автоматически оценивается на сервере; файлы и ответы доступны только ученику-владельцу и автору/администратору |
| `POST` | `/v1/submissions/{id}/run` | Повторно ставит в очередь только code submission со статусом `system_error` (`202 Accepted`); повторный запуск не расходует дополнительную попытку |
| `GET` | `/v1/submissions/{id}/file` | Скачивание вложения ответа через приватный endpoint; файлы хранятся вне публичной раздачи |
| `PATCH` | `/v1/submissions/{id}/grade` | Ручная проверка ответа автором курса или администратором с оценкой в пределах баллов задания и отзывом |

### Code Runner

Исходный код выполняется только отдельным Code Runner на выделенном runner host/VM,
не в Django, Celery worker или браузере. Backend кладёт в Redis только ID
submission; worker извлекает исходный код и hidden tests из общей базы и отправляет
их runner по HTTPS с `Authorization: Bearer ...`. Настройте одинаковый случайный
`CODE_RUNNER_TOKEN` в корневом `.env` и `code-runner/.env`, а
`CODE_RUNNER_URL` направьте на закрытый HTTPS endpoint runner.

Развёртывайте [code-runner/](../code-runner) только на отдельной VM, доступной
backend worker по firewall/VPN. Runner использует локальный Docker socket для
создания фиксированных одноразовых контейнеров; поэтому его VM является границей
доверия, а backend host не должен передавать свой Docker socket runner/backend
контейнерам. Ограничения sandbox: отключённая сеть, read-only filesystem,
ограничения CPU/RAM/PID/time, удаление контейнера после каждого hidden test,
отсутствие host mounts и привилегий. На VM предварительно загрузите только
фиксированные digest-pinned runtime images из `code-runner/main.py`.

Никогда не публикуйте runner напрямую в интернет: `code-runner/docker-compose.yml`
слушает только `127.0.0.1:8081`; завершайте TLS на reverse proxy и разрешайте
доступ только backend host. Не разворачивайте runner на той же машине, где
хранятся production secrets или данные, если изоляция runner host не обеспечена.
Runner возвращает только статус и агрегаты (баллы, число пройденных тестов,
время и память); stdout, stderr, входы и ожидаемые ответы hidden tests клиентам
не передаются.
`/health/` и `/api/health/` выполняют `SELECT 1` и подходят для liveness/readiness
проверки backend вместе с базой. Celery использует persistent Redis queue,
late-ack и task ID, чтобы повторная доставка после потери worker могла продолжить
тот же submission, не создавая дополнительную попытку.

Статусы code submission: `pending`, `running`, `passed`, `failed`, `timeout`,
`runtime_error`, `compile_error`, `system_error`. Язык копируется в submission
при отправке, поэтому последующее редактирование задания не меняет runtime для
уже отправленного кода. После первой code submission backend запрещает менять
баллы, язык, лимиты и hidden tests этого задания, чтобы queued/повторные задания
оценивались по неизменяемому контракту. Новое принятое code submission
расходует одну попытку; повторная отправка создаёт новую запись и расходует
следующую разрешённую попытку. Повторить запуск существующей записи можно только
после `system_error`, это не расходует новую попытку. Учёт попыток сериализован
блокировкой задания, чтобы параллельные POST не обходили `max_attempts`.
Минимальный лимит памяти code assignment — 64 МБ для обоих поддерживаемых
runtime; миграция повышает только старые code assignments, настроенные ниже
этого лимита.

## Формат ошибок

Все ошибки API (400, 404, 500) автоматически форматируются с гарантированным полем **`detail`** (через `api/exceptions.py`), что позволяет фронтенду корректно выводить понятный текст ошибки пользователю:
```json
{
  "detail": "Неверный логин или пароль"
}
```

## Настройки окружения и база данных

Backend использует кастомную модель `api.User`, роли `student`, `teacher`,
`admin`, а также отдельные профили ученика и преподавателя. Профили создаются
автоматически при создании пользователя; миграция переносит существующие
аккаунты в соответствующие таблицы.

Для локального запуска Django загружает `backend/.env`. Скопируйте
`backend/.env.example` в `backend/.env` и укажите реквизиты существующей
PostgreSQL-базы. Пароль PostgreSQL и Django secret key не имеют встроенных
production-значений: при `DJANGO_DEBUG=0` приложение останавливается с явной
ошибкой, если секреты или пароль БД не заданы. Для тестов допустимо явно
выбрать SQLite через `USE_SQLITE=1`.

Для Docker Compose скопируйте корневой `.env.example` в `.env` и замените все
значения `replace-with-...` случайными секретами и своими настройками домена.
Compose теперь не запускает базу и backend с общими паролями, wildcard-hosts
или открытым CORS по умолчанию.

## Локальный запуск (без Docker)

1. Активируйте виртуальное окружение:
   ```bash
   # Windows PowerShell:
   .\.venv\Scripts\Activate.ps1
   # или Linux/macOS:
   source .venv/bin/activate
   ```
2. Установите зависимости:
   ```bash
   pip install -r requirements.txt
   ```
3. Создайте `.env` (или скопируйте `.env.example`):
   ```bash
   copy .env.example .env
   ```
   Укажите в `POSTGRES_PASSWORD` пароль существующего локального PostgreSQL
   пользователя. Django автоматически загружает `backend/.env`; переменные,
   переданные процессу или Docker, имеют приоритет над значениями файла.
   Для разработки без PostgreSQL установите `USE_SQLITE=1`.
4. Примените миграции:
   ```bash
   python manage.py migrate
   ```
5. Заполните базу демо-данными:
   ```bash
   python manage.py seed_demo
   ```
   *Только для локальной разработки создаются тестовые аккаунты:*
   - Студент: `student` / `student123`
   - Администратор: `admin` / `admin123`

   Не используйте эти demo credentials в production. Если demo-аккаунты уже были
   созданы ранее, их пароли нужно сменить отдельно.
6. Запустите тесты:
   ```powershell
   $env:USE_SQLITE = "1"
   $env:DJANGO_DEBUG = "1"
   python manage.py test api --noinput
   ```
   
7. Запустите сервер разработки:
   ```bash
   python manage.py runserver 0.0.0.0:8000
   ```

## Запуск через Docker Compose

В корне проекта:
```bash
docker compose up --build -d
```
Бэкенд автоматически:
1. Дождется запуска PostgreSQL.
2. Применит все миграции.
3. Пропустит сидирование демо-пользователей по умолчанию. Чтобы явно включить
   демо-данные и стандартные demo-аккаунты, задайте `SEED_DEMO_DATA=1`.
4. Для новой production-базы создайте первого администратора вручную:
   ```bash
   docker compose exec backend python manage.py createsuperuser
   ```
   Не включайте demo-seeding на production. Если база уже содержит демо-аккаунты,
   отключение seeding не меняет существующие данные — смените пароли этих
   аккаунтов вручную.
4. Запустит сервер на порту `8000`.
